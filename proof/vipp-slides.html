VIPP Search Harness · Architecture Note

You don't write the search.
You orchestrate the agent that runs it.

A harness turns the archive into skills an agent commands, and turns the team from search operators into agent orchestrators. This is not a search box with an LLM bolted on, and it is not a workflow. It is an agent runtime whose skills happen to be retrieval.

Harness, not workflow

Who owns the control flow: the code, or the model?

A workflow's path is authored in code, so the same probe always takes the same route. A harness lets the model read what it found and choose the next move, so the same probe may take a different path every time.

Workflow · fixed path
the code decides the route
embed→ vector search→ rerank→ fuse→ answer
identical path, every run · no dial for depth
Harness · the model steers
the model decides the route
model chooses ↻
vectortexthybrid transcriptionmultimodallookup
observe results · decide again · until it answers

The loop

The model steers a bounded loop until it answers.

In the eval, one probe drove seven searches across six phrasings; another answered in two. Same system, model-chosen depth. A pipeline has no dial for that; a harness is nothing but that dial.

The skills

Six retrieval skills the agent commands over MCP.

The tools are the search-specific part; everything around them is a generic agent harness. A better model expands what these skills can do, it does not replace them.

vector_search
dense embeddings
Semantic nearest-neighbour over the embedded archive. The default probe when the phrasing is loose.
text_search
lexical / BM25
Exact-term and keyword matching, for names, codes, and quoted phrases the model must not paraphrase.
hybrid_search
vector + lexical
Fuses dense and sparse signals, so a probe gets both meaning and exact matches in one call.
transcription_search
spoken content
Searches speech-to-text transcripts, so the agent can find a moment by what was said, not just shown.
multimodal_search
vision + text
Searches the frames themselves, so the agent can retrieve a scene by what it looks like.
scene_lookup
direct fetch
Resolves a known id straight to its scene and metadata, the cheap move once the target is pinned.
