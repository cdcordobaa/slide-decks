The MIP evaluation harness — two-phase video-pipeline scoring, statistical rigor, a multimodal judge, cloud batch jobs — was grown as roughly ten written-down changes. The team never sat in the editor. It decomposed intent into discrete units of work, handed each unit to a coding agent, and steered by written record — a proposal, a design, a checklist. Authorship was the agent's job. Orchestration was ours.

The operating model

The specification is the interface between human intent and machine work.

An operator states intent as a written spec. A coding agent reads it — together with the project's standing context — and implements it. Skills carry the work to the cloud. Every run feeds a result back into the next spec. The human moves left-to-right by writing, not by typing code.

An orchestrator does not describe the work turn by turn. It sets durable operating guidance once, then hands over discrete units — so every agent, on every change, starts from the same rules without being re-told. That guidance lives in Markdown.
The agent's operating manual is Markdown — read before any unit of work

The unit of work

Every feature is one change — and every change is the same three files.

A change moves the system from one agreed state to the next. Its shape is the heart of the method: the why, the how, and the checklist — written, in that order, before a line ships.

proposal.md
// why, and what changes?
  • The pain, stated as a numbered problem list
  • What changes — capabilities modified / new
  • An explicit Non-Goals fence, drawn immediately
Fenced non-goals later reopen as their own scoped changes — the fence becomes the roadmap.
design.md
// how — the load-bearing decisions
  • Numbered decisions, each with its rationale
  • The rejected alternatives, named, with reasons
  • A closing Deferred / Non-Goals list
e.g. “keep our own ~100 lines” over migrating to a managed eval service — full prompt control, named and defended.
tasks.md
// the checklist + its status
  • A behavioral Principle stated before the tasks
  • Numbered, checkable units — tests included
  • A Status header carrying the validating result
“NO SIGNAL at N=5 despite a raw 10-vs-3 tally.” The proof, recorded in the spec.
The cadence

One change runs this loop. The harness is ten of them in sequence.

A concrete pain surfaces from running the last version; it becomes a proposal, a design, a checklist; the agent implements; a real eval validates; the folder is archived — and its result seeds the next problem.

  1. 01Propose
    State the pain as a numbered list. Draw the Non-Goals fence immediately.
  2. 02Design
    Make the load-bearing decisions — and name the rejected alternatives with reasons.
  3. 03Tasks
    Break it into checkable units. State the behavioral principle first.
  4. 04Implement
    The agent ticks the boxes and writes the tests the tasks named.
  5. 05Validate
    Run a real eval; record the outcome in the status line — the result is part of the spec.
  6. 06Archive
    Move to archive/<date>-<name>. Its result seeds the next change.

The deployment layer

Skills are how the orchestrator operates — reusable, named procedures the agent invokes.

Each skill absorbs a unit of work the operator would otherwise repeat by hand — the operator invokes it by name instead of remembering flags, and the flow ends on the cloud by standing rule. Some already existed; others were the obvious next skill the moment a pattern repeated twice.

  • openspec-propose
    Describe what you want; get a complete proposal + design + tasks, ready to implement.
  • mip-eval-run
    Operate the harness end-to-end — generate candidate batches (Phase 1) and evaluate against a baseline (Phase 2).
  • prompt-sync
    Pull the live production prompts out of the workflow YAML into a candidate config — so a prompt change is a clean, isolated arm.
  • rubric-sync
    Author and version a judge rubric from a dimension spec — bump rubric_version + rubric_sha, guaranteeing the migration never changes verdicts.
  • dimension-add
    Scaffold a new judged dimension end-to-end: extend the dimensions parameter, wire the rubric, the report, and the datastore entity.
  • dashboard-sync
    Publish the read-only Streamlit dashboard and reconcile the mip-eval-runs entities after a run.

Skills fire Cloud Run Jobs

mip-eval-batch-runner
Phase 1 — generate candidate assets; triggers the video-processing Cloud Workflow over a manifest slice.
mip-eval-phase2-runner
Phase 2 — judge two batches multimodally, aggregate, persist to the dashboard datastore.
STANDING RULE · both phases default to the cloud, never the laptop. Local runs die on sleep; cloud jobs survive and finish server-side.
The capstone skill

One skill chains the whole toolkit into a single command.

Above those primitives sits the loop-closer. Every run this program did by hand was the same choreography — scaffold a change, derive the two arms, fire two cloud jobs, read the verdict, write it back, archive. /eval-change is the skill that runs it all: one hypothesis in, a closed, validated change out.

◇ The loop-closer — chains propose · run · validate · archive
.cursor/skills/eval-change/SKILL.md
---
name: eval-change
description: Turn one hypothesis into a closed OpenSpec
  change — scaffold the unit of work, derive both arms,
  run both cloud jobs, write the verdict back, archive.
reads: [ CLAUDE.md, memory/*, openspec/config.yaml ]
chains: [ prompt-sync, rubric-sync, mip-eval-run,
          dashboard-sync ]
enforces: [ cloud-first, candidate=flash-lite,
            N>=30-for-a-decision, principle-first-tasks ]
---

# Usage
# /eval-change "flash-lite v4 vs prod-2.5,
#              description-isolated, N=30"
  1. proposeScaffold the change — write proposal · design · tasks, pain + Non-Goals, the isolation-mode decision with its rejected alternative, and a principle-first empty status header.
  2. generateDerive both arms from the one-line hypothesis — the candidate batch.yaml, the import-baseline config, and the EvalSpec (rubric, judge, sample, decision thresholds).
  3. run · cloudFire both Cloud Run Jobs in order — Phase-1 generate, then Phase-2 judge — and poll. Never local (memory: run-everything-on-cloud).
  4. validateRead the verdict — parse SIGNIFICANT / NO-SIGNAL per dimension straight from the report.
  5. archiveWrite it back — fill the tasks.md status line with the validating result and stage the move to archive/. The loop closes itself.

Why it anchors the toolkit

  • The last program ran this by hand — building fresh-30 sets, batch yamls, and EvalSpecs, deploying jobs, topping N to a clean 30, reading verdicts, and folding results into the docs. A dozen steps, every time.
  • It would enforce the standing rules mechanically — cloud-first, flash-lite candidates, N ≥ 30 for a decision — instead of relying on the operator to remember each md file.
  • It makes the unit of work atomic: a hypothesis becomes a fully-scaffolded, run, and recorded change — the orchestrator states intent once and reviews a result, nothing in between.
  • It is a fenced non-goal made real — exactly how this method already turned “UI writes,” “transcription,” and “cloud jobs” into their own later changes.

The orchestrator's leverage: every operation the human repeats by hand is a skill waiting to be written. Name it once; invoke it forever.

Why it compounds

What spec-driven orchestration actually bought us.

01

The “why” is recoverable

Why swap-and-average, why the 0.65 bar, why import-baseline — each is one proposal away, with the rejected alternative named. New engineers inherit reasoning, not just code.

02

Pre-shaping made features data

A parameter left open in one phase — dimensions, a --mode namespace, rubrics-as-YAML — let the next phase plug in as configuration, not a rewrite.

03

The specs predicted the experiments

The canary written in Phase 2 is the A/A calibration study that ran months later. Writing the validation down first made it a plan, not an afterthought.

04

Deletion is a legitimate outcome

Phase 7 retired its own abstraction once it stopped earning its keep — the cleanest possible result, reachable only because the overlap was written down and visible.
