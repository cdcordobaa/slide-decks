VIPP Search Harness — An Agentic Harness for Retrieval
VIPP Search Harness · Architecture Note

You don't write the search. You orchestrate the agent that runs it.

A harness turns the archive into skills an agent commands — and turns the team from search operators into agent orchestrators.

Agent = Model + Harness 6 retrieval skills 8 event types MCP over stdio Gemini 2.5 Flash · pluggable ≤ 12 turns / run

Agent = Model + Harness. The model (Gemini) supplies the reasoning and is a pluggable component; everything else — the loop, tool dispatch over MCP, the result pool, sessions, verification, the snapshot trail — is the harness: the infrastructure that manages everything except the reasoning. This is not a search box with an LLM bolted on, and it is not a workflow. It is an agent runtime whose skills happen to be retrieval.

That reframes the team's job. You don't run queries — you compose the capabilities and set the guardrails; the agent composes the moves. And it was built the way it runs — by teams of orchestrated agents. Orchestration isn't a feature here; it is the operating model, top to bottom.

Harness, not workflow

Why this is a harness — not a workflow

The distinction isn't branding. It's the established line between two kinds of LLM system, and it decides exactly one thing: who owns the control flow — the code, or the model.

Workflow
"Systems where LLMs and tools are orchestrated through predefined code paths." The route is authored in code. Same input, same path, every time.Anthropic · Building Effective Agents
Agent
"Systems where LLMs dynamically direct their own processes and tool usage." An LLM using tools on environmental feedback, in a loop — choosing its own moves.Anthropic · Building Effective Agents
Harness
"The software infrastructure surrounding an AI model that manages everything except the model's actual reasoning." Agent = Model + Harness — the model is a pluggable part.agent-harness engineering · 2026

An agentic workflow sits between the first two — prompt-chaining, routing, orchestrator-workers — but the control flow is still authored in code: the LLM fills the steps, it doesn't choose them. This harness is the third thing. It lets the model own the path while the harness owns everything around the reasoning.

The tell: run the same probe twice

A workflow can't vary its path — that's its whole virtue. This harness varies constantly, because the model reads what it found and decides what's next. In the eval, one probe drove seven searches across six phrasings; another answered in two. Same system, model-chosen depth. A pipeline has no dial for that — a harness is nothing but that dial.

We used workflows to build the harness

The clean recursion: this harness was assembled by agentic workflows — deterministic scripts that orchestrated fleets of coding agents through fixed phases (scaffold → build → gate → adversarial review). That is the right tool for construction, where you want the same result every run. A harness is the right substrate for investigation, where you want the model to find a path you couldn't script. The team practised both — orchestrating agents to build the thing that orchestrates agents.

Grounded in the current literature: Anthropic, Building Effective Agents (workflow vs agent); and the 2026 agent-harness engineering definition (Agent = Model + Harness).

MCP & skills

Capabilities in a registry, spoken over a protocol

Each skill is a small object — an id, a description, a frozen JSON schema, and a run() that does all its I/O through an injected context. The registry hands them to the MCP server as tools; the same registry, the same skills, would serve any MCP client.

Because I/O is injected, the whole harness runs offline against recorded fixtures (HARNESS_FIXTURES=1) — no credentials, no live traffic — which is how every test and gate verifies behaviour without touching prod.

scene_desc_vector_search
SC-VEC-D · scene_embedding 1536d
Semantic search over scene descriptions. Embeds the query inline, finds nearest neighbours. Best for conceptual / paraphrastic probes.
scene_desc_text_search
SC-DESC · full_description
Keyword search over the description field. Best when exact wording matters and the phrase is likely present verbatim.
scene_hybrid_search
SC-HYB · RRF, desc + transcription
Server-side reciprocal-rank fusion over what was shown and what was said. Best when evidence is split across both.
scene_transcription_vector_search
SC-VEC-T · transcription_embedding
Semantic search over spoken transcription. Best for finding who said what — reporters, officials, quotes.
multimodal_vector_search

Search the multimodal index over video/frame assets. Reaches visual similarity the text channels can't.

Agent skills · the know-how layer

Two senses of "skill": what it can do, and how it knows to do it well

◆ designed & approved · the 6 tools are live today, the playbook layer is next

The six retrieval skills above are tools — they extend what the agent can do. There is a second, industry-standard sense the harness is gaining: Agent Skills — progressively-disclosed markdown know-how that extends how well it does it. MCP gives the agent tools; a skill file gives it methodology.

Capabilities — the tools it calls
The 6 retrieval skills, over MCP: vector, text, hybrid, transcription, multimodal search, and scene lookup. Frozen schemas, always available. What the agent can reach.
Agent Skills — the know-how it reads
Markdown playbooks: when to prefer hybrid over vector, the distinct-phrasing discipline, filter recipes, worked examples from the eval. Loaded when relevant, free until then. How the agent uses the tools well.

Why the method is load-bearing

The eval proved it. A1 failed at 3/10 for one missing instruction — the agent searched both channels, but with the same query string. A single line of method ("word every search distinctly") took it to 10/10. Today that method is compiled into system-prompt.ts, so changing a sentence meant a spec change and a redeploy. The skills layer moves the method into an editable playbook — and makes the same know-how available to any client driving these tools, not just this UI.

One source of truth, delivered over every surface

A single canonical playbook — backend/harness/skills-doc/investigation.md — is the only hand-edited file. Everything else either reads it live or is a generated, hash-verified copy. Sameness across clients isn't a protocol guarantee; it's a build guarantee.

The layering is deliberate. A few invariants stay baked in code (cite sceneIds, natural-language queries). The method lives in the startup-loaded playbook — edit the file, restart, behaviour changes, no rebuild. MCP's own instructions field carries a short summary to every connecting client. And the full skill ships as SKILL.md where a client will reliably trigger it. Discipline that must always hold is never left to a resource the model might forget to read — that is the lesson A1 taught, encoded into the architecture.

The pool and the snapshot

As results stream in, a pure reducer folds them into a result pool: deduped by sceneId, keeping the best score, recording which queries surfaced each scene and whether it was looked up. In a session, that pool is seeded into the next probe — so "narrow those to under 30 seconds" refines what's already found instead of starting over.

At the end, exactly one Run snapshot is written to runs/<ulid>.json — the full event log, the pool, the answer, embedding vectors stripped. Any MCP client can read it back through the vipp://runs/{'{'}runId{'}'} resource. The transcript is the audit trail.
